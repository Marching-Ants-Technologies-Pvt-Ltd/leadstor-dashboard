## 4. Database Models & Tables

* **Connected Database**: ❌ **None directly.** This is a pure frontend — it holds **no** ORM models, migrations, or DB drivers.
* **Data Access Pattern**: All persistence is delegated to the shared PHP backend (`dashboard` repo) via REST.
  * Client-side calls go through `src/utility/xFetch.jsx` → `xFetch({ method, path, payload })`
  * Base URL: `process.env.NEXT_PUBLIC_LEADSTOR_REST`
  * Auth: `Authorization: Bearer <access_token>` (token in `localStorage.access_token`)
  * Session/state cached in `localStorage` (`CurrentSessionData`, `LeadOwnersById`) via `src/utility/TinyDB.jsx`
* **Migration Rule**: Schema changes must be authored as standalone `.sql` files **in the `dashboard` (PHP) repo**, never here. Execute manually per the org `.sql` policy.

## 6. Known Gotchas & Cross-Entity Blast Radius

### Cross-Entity / Cross-Repo Dependencies
* **`dashboard` (PHP 7.x shared API)** — The single most critical dependency. **All** CRM data flows through `/services/*`. Any breaking change to these REST contracts breaks this frontend. Changes to lead/enquiry/admission/attendance endpoints affect **both** Leadstor and ConceptNinjas.
* **`conceptninjas` API (`CONCEPTNINJAS_URL`)** — Auth bridge: `src/lib/conceptninjas/oauth.js` POSTs to `signupWithEmail` / `oauth` for credential + social login. Shared auth path across entities — treat as shared infrastructure.
* **`cn-cron-jobs`** — Downstream consumer of the same DB (email queues, WhatsApp reminders, payment notifications). Frontend actions (e.g. `sendPaymentNotification`, `sendTestInvitationEmail`) may enqueue work processed by cron.

### Architecture Notes & Risks
* **Auth is dual-layered & partially in-memory**: NextAuth JWT coexists with a separate `localStorage` `access_token` returned from the PHP backend. `access_token` drives `xFetch`; `CurrentSessionData` drives UI. Token expiry is checked every 5 min (`utility/auth.js` → `AuthService`). Note: `[...nextauth]/route.jsx` uses a **module-scoped `currentUser` variable** — risky under concurrent serverless invocations on Vercel.
* **Client-side route guarding only**: `(dashboard)/layout.jsx` enforces auth in the browser (no middleware). No `middleware.ts` present — every dashboard page renders then redirects.
* **Session state read from `localStorage` at module load** (`utility/TinyDB.jsx`) — can be empty on first render / SSR; guard against `{}` defaults.
* **Backend `oauth` signup detection** is heuristic: `suffix = (auth_provider === 'EMAIL' && first_name.length > 3) ? 'signupWithEmail' : 'oauth'` — fragile coupling to input length.
* **Mixed TS/JS + `.jsx` under App Router**: root `layout.tsx` is TSX while many routes are `.jsx`; `tsconfig` has `allowJs: true`. Keep types consistent when adding files.
* **`experimental_ppr = true`** exported in `(dashboard)/layout.jsx` (Partial Prerendering) — confirm Next.js 14.2 support/behavior when changing dashboard rendering.
* **Legacy/brand drift**: `tailwind.config.ts` defines a `leadstor` palette in **pink/lavender/violet** (`#F1BBEA`), while newer `(dashboard)` screens use **blue** gradients (`blue-500/600`). Inconsistent brand tokens — not yet aligned to the AGENTS.md brand system.
* **`next.config.mjs`** only whitelists `api.dicebear.com` for remote images — adding new external image hosts requires config updates.
* **`README.md`** is still the create-next-app boilerplate; the site "version" is tracked in `leadstor.config.js` (`Version = "v1.0.3"`).

### Safe-Change Checklist for Agents
1. Treat all `/services/*` endpoint shapes as a **contract** shared with the `dashboard` PHP backend — inspect real schemas before editing payloads.
2. Never add DB migrations here; those belong in `dashboard` as manual `.sql` files.
3. After changes: `npm run build` must pass with zero TS/ESLint errors; verify dashboard auth redirect + `xFetch` 401 handling.
4. Do not push to production Vercel directly — open a PR for the human gatekeeper.
